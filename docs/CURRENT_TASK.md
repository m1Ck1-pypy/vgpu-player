## Задача

Дать плееру воспроизведение по `http(s)://` без регрессий для локальных
файлов: свой `HttpReader` с `Range`, таймаутами, повторами и отменой;
`MediaReady.seekable` берётся из ответа сервера; звук по URL — только FFmpeg;
`Event::Buffering` и плашка «Буферизация…»; панель «Файл» / «URL» в UI.
HLS (`.m3u8`) остаётся этапом 5.

## Решения (этап 2, на одобрение)

20. ✅ `player.rs` (~1500 строк) делим **до** правок логики: `media.rs` —
    `Media`, `MediaInfo`/`VideoTrackInfo`/`AudioTrackInfo`, `probe_tracks`,
    `MediaReady`; `engine.rs` — `run_engine`, `AudioSink`, часы, синхронизация,
    спектр; `player.rs` — только `Player`, каналы и тесты. Это механический
    перенос (подэтап 2.0), публичные пути через `lib.rs` не меняются.
21. `MediaReady { media_info, video_info, duration, seekable, live }`
    собирается из уже открытой `Media`: `seekable = source.as_file().is_some()`
    (для URL — по ответу `HttpReader`, этап 3), `live = false`.
22. Ошибка открытия не завершает поток: `media = None`, ядро продолжает
    принимать `Open`/`Stop`; `Play`/`Seek` без медиа игнорируются с `debug!`,
    а не копятся.
23. Отмена открытия — два атомика: `cancel: Arc<AtomicBool>` (общий с
    декодерами) и `open_seq: Arc<AtomicU64>` для повторов. `Stop` и `Drop`
    взводят `cancel` **до** отправки команды; новый `Open` увеличивает
    `open_seq`, и текущее открытие видит, что его заменили. Проверка обоих —
    между шагами открытия (звук, видео, проба), поэтому отмена укладывается
    в ≤ 2–3 с.
24. Звуковое устройство открывается лениво при первом источнике со звуком.
    Ошибка устройства уходит `Event::Error`, видео продолжает играть (§3.2 SPEC).
25. Новый `Open` всегда сначала освобождает прежнюю `Media`. Отменённое
    открытие не присылает ни `Ready`, ни `Error` — иначе UI получит метаданные
    отменённого источника.
26. Для тестов — скрытый конструктор `#[cfg(test)] Player::open_with(source,
opener)`: «медленный читатель» без сети, без новых файлов и без `mockall`.
27. ✅ Одно ядро на плеер (вариант A): `VideoPlayer` держит `Player` и шлёт
    `Command::Open`. Новый поток создаётся только при первом `open` или после
    `EngineGone`. Разбор альтернативы — раздел «Одно ядро на плеер».
28. `preview_frame` — только для `Source::File` и не для `.m3u8`; для URL
    кадр появится первым кадром из ядра.
29. `run_app(Option<PathBuf>)` сохраняется, URL — через
    `run_app_source(Option<Source>)`; `player-app` разбирает аргумент
    `Source::from_os_string` и не считает `https://…` путём.

Одобрено владельцем 2026-11-20: 20 (с уточнением про отдельные файлы),
21–29. Вариант A («одно ядро») выбран и зафиксирован в решении 27.

## Решения (этап 3, действуют)

30. HTTP-читатель — отдельный файл `player-core/src/http.rs` (не раздуваем
    `player.rs`/`media.rs`): `HttpConfig`, агент, `HttpReader` и его тесты.
31. `ureq` включён с `default-features = false, features = ["native-tls"]`;
    провайдер и корни задаются явно (`TlsProvider::NativeTls`,
    `RootCerts::PlatformVerifier`).
32. Первый запрос — `GET` с `Range: bytes=0-0`: даёт длину, `seekable` (206)
    и `Content-Type`. Дальше чтение окном 2 МиБ, `seek` перезапрашивает
    `Range`. `HEAD` не используем — он может врать про `Range`.
33. Повторы: 5 попыток с паузами 0.25/0.5/1/2 с, только для таймаутов/5xx/
    обрыва; 4xx — сразу ошибка. Понятный текст вместо `invalid data`
    от FFmpeg даёт слот `HttpFailure`.
34. Продолжение после обрыва — **вариант B** (выбор владельца): с `Range` —
    с текущей позиции; без `Range` — перезапуск и пропуск уже прочитанного,
    пока позиция ≤ 64 МиБ, иначе `NotSeekable`.
35. `open_reader(source, cancel) -> OpenedReader { reader, failure, buffering }`;
    звук по URL — только FFmpeg (Symphonia требует `Read + Seek`);
    `seek` при `!seekable` — no-op в ядре и в UI.
36. `Buffering` — атомик в читателе, движок шлёт событие только после 200 мс
    блокирующего чтения (без мигания); для сети очередь звука — 32 блока.

## Одно ядро на плеер или поток на каждое открытие

Был выбран **вариант A**: одно долгоживущее ядро, в него новый источник
приходит `Command::Open`. Вариант B — поток на открытие с собственной
отменой — рассматривался как альтернатива.

| Критерий                    | A: одно ядро                                                                                        | B: поток на открытие                                                                       |
| --------------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Звуковое устройство         | открыто один раз, уровень и mute живут                                                              | переоткрывается на каждый файл; на время перекрытия — два потока WASAPI                    |
| Сеть (этап 3)               | одно соединение: старый `Open` отменяется до нового                                                 | старый поток может висеть в `Media::open` и качать вместе с новым — двойной DNS/TLS/трафик |
| Отмена                      | два атомика в `Player`, опрос между шагами                                                          | свой флаг каждому потоку, но нет точки ожидания завершения                                 |
| Состояние                   | один автомат: `media: Option<Media>`, `Loading`/`Ready`/`Error`                                     | состояние размазано по живым потокам                                                       |
| Логи/замеры                 | один поток, последовательные записи                                                                 | логи двух ядер переплетаются, замер трафика (этап 4) загрязняется                          |
| Сложность                   | `Play`/`Seek` без медиа игнорируются; `Open` во время открытия требует `open_seq` и дренажа очереди | нужно обеспечить, чтобы старый поток не держал устройство и не качал после `Drop`          |
| Восстановление после паники | нужен явный `EngineGone` → новое ядро (2.4)                                                         | новый `open` уже создаёт новое ядро                                                        |

Вариант B даёт изоляцию попыток (свежие канал и epoch), но не даёт главного —
гарантии, что после `Drop` старый поток перестал качать и держать звук. При
блокирующем `Media::open` (HTTP на этапе 3) окно перекрытия непредсказуемо.
Вариант A укладывается в SPEC §3.2 и уже учтён в 2.2–2.4: `Option<Media>`,
`Play`/`Seek` без медиа игнорируются, `open_seq` отменяет текущее открытие,
после отмены ядро дренирует команды и берёт последний `Open`.

**Решение:** A — реализовано в 2.4. Вариант B оставлен как отвергнутая
альтернатива: он не даёт гарантии, что после закрытия окна остался один
источник и один звуковой поток.

**Что нужно для этапа 3:** прямая ссылка на один файл, например
`https://host/path/movie.mp4` (или `.mkv`/`.webm`/`.mp3`). Признаки:

- `Content-Type: video/mp4` (или `audio/mpeg` и т.п.), а не `text/html` и не
  `application/vnd.apple.mpegurl`;
- в браузере открывается/скачивается один файл, URL не заканчивается `.m3u8`;
- `Range`-запрос `curl -r 0-0 -I <url>` отвечает `206 Partial Content`.

HLS-ссылка пригодится на этапе 5; если у CDN есть прямой MP4-рендишн
(тот же путь без `.m3u8`), подойдёт он.

## Что войдёт в этапы 1–5, а что нет

| Источник                                          | После этапа 5                                                                   |
| ------------------------------------------------- | ------------------------------------------------------------------------------- |
| Локальный файл, `file://`                         | ✅                                                                              |
| Прямой `http(s)://…/movie.mp4` (MP4/MKV/WebM/MP3) | ✅ этап 3                                                                       |
| HLS (`…/index.m3u8`, включая ссылку rtbcdn)       | ✅ этап 5, если выбран вариант A или B                                          |
| DASH (`.mpd`), Smooth Streaming                   | ❌ отдельный этап                                                               |
| YouTube, VK, Rutube и другие страницы-сайты       | ❌ вне рамок: нужен извлекатель потоков (yt-dlp и подобные), а не HTTP-читатель |
| DRM (Widevine/PlayReady)                          | ❌ вне рамок                                                                    |

YouTube отдаёт не файл, а HTML-страницу, а видео — через внутренний API
отдельными адаптивными потоками с подписью и ограничениями. Это отдельная
