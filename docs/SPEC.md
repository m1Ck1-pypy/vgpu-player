Сознательные упрощения (не баги):

- пороги синхронизации (10 мс вперёд, 50 мс опоздания) подобраны по замерам и
  могут уточняться;
- точная перемотка на файле с большим GOP занимает ~0.2–0.4 с: на это время
  звук и видео замирают вместе, затем продолжаются с целевой позиции;
- удержание стрелок отправляет `Seek` на каждое нажатие; троттлинг добавим,
  если на слабой машине будет заметно;
- состояние `Loading` не введено: локальный файл открывается синхронно и
  мгновенно, показывать промежуточный экран нечему; индикатор буферизации
  убран из контракта вместе с `Event::Buffering`;
- файл демо-приложения по-прежнему можно передать аргументом; выбор мышью —
  через `O`/`Ctrl+O`, пункт меню «Открыть…» или перетаскивание; кнопки
  «Открыть» в панели нет.

Сборка и запуск на Windows (детали — раздел 12.4):

```bash
# один раз на машине
git clone --depth 1 https://github.com/microsoft/vcpkg.git .tools/vcpkg
.tools/vcpkg/bootstrap-vcpkg.bat -disableMetrics
.tools/vcpkg/vcpkg install "ffmpeg[avcodec,avdevice,avfilter,avformat,swresample,swscale,dav1d]" --triplet x64-windows --recurse
cp .tools/vcpkg/installed/x64-windows/bin/*.dll target/debug/
cp .tools/vcpkg/installed/x64-windows/bin/*.dll target/debug/deps/

cargo run -p player-app -- assets/test/audio_only.m4a
cargo run -p player-cli -- assets/test/audio_only.m4a
```

в его `PATH` первым может оказаться `/usr/bin/link.exe` вместо MSVC (детали —
раздел 12.4).

## 1. Назначение и пользователь

Учебный проект владельца. Главная цель — **понять каждую строку и научиться
Rust**, а не получить готовый плеер.

Продукт: плеер локальных видеофайлов со звуком и плавной картинкой.

Функциональность релиза: play/pause, перемотка, громкость, полноэкранный
режим.

Платформы: уточняются в процессе; по умолчанию разрабатываем на ОС, где
запущен агент (в текущей сессии — Windows).

## 2. Правила процесса (обязательны для агента)

1. Один этап за раз; переход к следующему — только по явному согласию.
2. Сначала план, потом код: кратко описать изменения и затронутые файлы, ждать
   «ок» для всего, что больше ~50 строк.
3. Новые концепции Rust объяснять в 2–4 предложениях; ошибки компилятора
   объяснять по причине, а не только исправлять.
4. Ключевые части — скелет с `todo!()` и комментариями, реализацию пишет
   владелец, затем агент делает ревью:
   - аудио-часы,
   - очередь кадров,
   - логика перемотки (epoch).
     Рутину (UI-разметка, обработка ошибок, тесты, boilerplate) агент пишет сам.
5. Один этап — одна ветка `stage-N-...`, коммиты маленькие, сообщения на
   английском: `feat(core): ...`, `fix(gpui): ...`.
6. Новая зависимость — только после согласования (причина + альтернатива).
7. Не переписывать чужой код «заодно»; о найденной проблеме сообщать.
8. Честность важнее скорости: не угадывать API GPUI/FFmpeg/rodio, а проверять
   по docs.rs или исходникам.
9. Ничего не запускать и не устанавливать глобально (системные пакеты, `sudo`,
   конфиги вне репозитория) без разрешения.

  player-gpui/               # БИБЛИОТЕКА UI: VideoPlayer, video_view, controls_view; без main

### 3.1 Публичный API библиотеки

`player-gpui` — библиотека без `main`. Запускаемый бинарник — отдельный крейт
`player-app`, он же служит примером использования.

| Экспорт                                         | Назначение                                                                     |
| ----------------------------------------------- | ------------------------------------------------------------------------------ |
| `VideoPlayer`                                   | сущность GPUI: состояние (`PlaybackState`), команды, опрос событий ядра        |
| `video_view(&Entity<VideoPlayer>, &App) -> Div` | виджет кадра; размер и скругления задаёт вызывающая сторона                    |
| `controls_view(&player, cx) -> Div`             | необязательная панель: кнопки-иконки (play/pause, звук, fullscreen) и слайдеры |
| `run_app(Option<PathBuf>)`                      | готовая обёртка запуска окна для бинарника                                     |
| `MediaInfo`, `VideoTrackInfo`, `AudioTrackInfo` | метаданные файла для панели «Информация о файле»                               |
| `gpui`, `gpui_platform` (реэкспорт)             | одна версия GPUI и платформенного слоя у библиотеки и потребителя              |

Подключение у потребителя: `player-gpui = { path = "..." }` или
`{ git = "https://github.com/m1Ck1-pypy/vgpu-player.git", tag = "v0.1.0", package = "player-gpui" }`.
Пошаговая инструкция — в `crates/player-gpui/README.md`; как встроить в чужое
gpui-приложение и какие есть примеры — раздел 14.

Основные методы `VideoPlayer`: `play`, `pause`, `toggle_playback`, `restart`,
`stop`, `seek`, `set_volume`, `toggle_mute`, `open`, `open_dialog` (системный
диалог), `open_dropped` (перетащенные пути), `retry`, `path`, `video_info`,
`media_info` (контейнер, кодеки, звук), `frame`, `stats`, `stats_visible`,
`set_stats_visible`, `toggle_stats`, `fullscreen`, `set_fullscreen`.

## 4. Архитектура

```
demux thread ─► audio decode ─► rodio (ведущие аудио-часы)
             └► video decode ─► ограниченная очередь кадров ─► UI забирает кадр по часам
```

Обязательные правила дизайна:

- **Ведущие часы — аудио.** Позиция = число реально отданных в устройство
  сэмплов (`AtomicU64`), а не таймер. Видео подстраивается под аудио. Для файла
  без звука — запасной монотонный таймер; им же доигрывается хвост видео,
  если звук закончился раньше.
- **Звук — два бэкенда за одним API.** Сначала Symphonia; если она не
  умеет кодек (например, Opus в WebM/MKV) — FFmpeg. Оба отдают ядру один и
  тот же `AudioChunk` с `f32`, часы и rodio о подмене не знают.
- **Видеодекодер за трейтом** `VideoDecoder`, чтобы backend (ffmpeg-next или
  другой) менялся без переписывания остального.
- **Очередь кадров ограничена** (3–6 кадров). Неограниченных каналов для кадров
  нет.
- **UI-поток никогда не блокируется** на ожидании кадров или IO; забирает
  только готовое.
- **Перемотка через epoch** (номер поколения): после seek всё, что пришло со
  старым epoch, отбрасывается.
- **Перерисовка только** при новом кадре или смене состояния.
- Все таймстемпы приводятся к `Duration` на границе ядра.

## 5. Контракт команд и событий

| Команды UI → ядро | События ядро → UI  |
| ----------------- | ------------------ |
| `Open(path)`      | `DurationKnown`    |
| `Play`            | `PositionChanged`  |
| `Pause`           | `NewFrame`         |
| `Seek(Duration)`  | `Ended`            |
| `SetVolume(f32)`  | `Error`            |
| `Stop`            | `Stats(SyncStats)` |

Транспорт — `crossbeam-channel`; очередь кадров ограничена, каналы команд и
событий — нет (обоснование — при реализации).

Кадры не идут событием `NewFrame`: для них есть отдельный ограниченный
канал и аксессор `Player::try_recv_frame`, а метаданные видео доступны сразу
через `Player::video_info()` (решение 2026-11-16, раздел 11.5). `NewFrame`
остаётся зарезервированным именем контракта, фактически не используется.
`Buffering` убран на этапе 7: локальные файлы не буферизуются.

Ядро отправляет `DurationKnown`, `PositionChanged`, `Stats`, `Ended`, `Error`.
`Stats` приходит раз в 500 мс во время воспроизведения: fps, число показанных
и пропущенных кадров, отставание.

## 6. Стек

- GPUI через `gpui-fast`, подключённый как `gpui = { package = "gpui-fast" }`.
  Не смешивать с upstream `gpui` или `gpui-pre` в одном workspace.
  `player-gpui` реэкспортирует `gpui`, чтобы у потребителя была та же версия.
- `rodio` 0.23 — только вывод: `default-features = false, features = ["playback"]`,
  чтобы его собственные декодеры не дублировали Symphonia. `symphonia` 0.5.5 с
  `features = ["all"]` — основной демукс и аудиодекодер. Кодеки, которых нет в
  Symphonia 0.5.5 (например, Opus в WebM/MKV), декодируются через FFmpeg; оба
  бэкенда отдают ядру один и тот же `AudioChunk` с `f32`, поэтому часы и rodio
  от этого не зависят. `cpal` напрямую не подключаем: версия должна совпадать с
  версией у `rodio`.
- API-особенность: в `rodio` 0.23 бывший `Sink` называется `Player`, а
  устройство открывается через `DeviceSinkBuilder::open_default_sink()`.
- `ffmpeg-next` 9.1 (нужны dev-библиотеки FFmpeg 9), `image` (dev, PNG-дампы).
  Сборка проекта включает `libdav1d`: встроенный декодер AV1 в FFmpeg умеет
  только аппаратное декодирование, а нам нужно программное.
  В Cargo зависимость названа `ffmpeg` (`package = "ffmpeg-next"`): сама
  библиотека собирается с именем `ffmpeg`, и код использует `ffmpeg::...`.
- `crossbeam-channel`, `thiserror` (библиотеки), `anyhow` (бинарники),
  `tracing`, `clap`.
- Версии задаются в `[workspace.dependencies]` корневого `Cargo.toml`; в крейтах
  — `dep.workspace = true`.
- `gpui-fast`/`gpui-fast-platform` — **0.1.16** (проверено по docs.rs
  2026-11-16). Фичи `wayland`/`x11` — Linux-бэкенды, включаются только под
  `cfg(target_os = "linux")`.
- MSRV проекта — **1.98**: столько требует `gpui-fast` (его
  `rust-toolchain.toml`).
- Зависимости подключаются по этапам: 0 — `gpui`, `gpui_platform`; 1 —
  `rodio`, `symphonia`, `crossbeam-channel`; 3 — `ffmpeg-next` 9.1 и `image`
  (dev, PNG-дампы); 7 — `thiserror`, `anyhow`, `tracing`,
  `tracing-subscriber`; 9 — `rfd`.

## 7. Ошибки и состояния UI

- `thiserror` в `player-core` и `player-gpui`; `anyhow` только в бинарниках.
- Библиотеки пишут диагностику через фасад `tracing`; подписчик
  (`tracing-subscriber`, `RUST_LOG`) ставится в `player-app` и `player-cli`.
- Без `unwrap()`/`expect()` в рабочем коде (в тестах допустимо).
- UI-состояния (`PlaybackState`): `Idle`, `Ready`, `Playing`, `Paused`,
  `Ended` (кнопка «Повторить» и `Replay` в панели), `Failed` (текст ошибки и,
  если путь известен, кнопка повторного открытия). Состояние `Loading` не
  введено: файл открывается синхронно.
- `player-cli` при ошибке завершается с кодом `1` (`ExitCode::FAILURE`) и
  сообщением в stderr; ключевые события и ошибки также видны в логах.

## 9. Тестовые данные

Лежат в `assets/test/`. Крупные файлы не коммитим: игнорируем в `.gitignore` и
описываем, как сгенерировать.

```bash
# видео со счётчиком кадров и писком раз в секунду, для A/V-синхронизации
ffmpeg -f lavfi -i testsrc2=size=1280x720:rate=30 \
       -f lavfi -i "sine=frequency=1000:beep_factor=4" \
       -t 30 -c:v libx264 -pix_fmt yuv420p -c:a aac assets/test/sync_test.mp4
# то же в WebM (VP9 + Opus)
ffmpeg -f lavfi -i testsrc2=size=1280x720:rate=30 -f lavfi -i "sine=frequency=1000" \
       -t 30 -c:v libvpx-vp9 -c:a libopus assets/test/sync_test.webm
# короткий AV1-клип для проверки libdav1d (без перекодирования из любого AV1)
ffmpeg -hide_banner -loglevel error -y -i assets/test/test_10min.webm \
       -t 2 -c copy assets/test/av1_test.webm
# 10 минут 1080p30 для замера производительности (звук — тишина, чтобы не шуметь)
ffmpeg -f lavfi -i testsrc2=size=1920x1080:rate=30 \
       -f lavfi -i anullsrc=channel_layout=stereo:sample_rate=44100 \
       -t 600 -c:v libx264 -preset ultrafast -crf 28 -pix_fmt yuv420p -g 60 \
       -c:a aac -b:a 128k assets/test/bench_10min_1080p.mp4
```

Дополнительно нужны: только звук, только видео, пустой, обрезанный, файл с
неподдерживаемым кодеком.

## 10. Стиль кода и «готово»

- Edition 2024. Без `unsafe`, кроме FFI к FFmpeg, с комментарием `// SAFETY:`.
- Публичный API ядра — небольшой, с `///`. Внутренности — `pub(crate)`.
- Каналы и атомики вместо `Mutex` там, где это естественно; `Mutex` — только с
  объяснением.
- Комментарии и документация на русском, идентификаторы на английском.
- Тесты рядом с кодом (`#[cfg(test)]`) для синхронизации, очереди, epoch,
  преобразования времени; интеграционные — в `tests/`.

«Готово» для этапа:

## 11. Решения по расхождениям (2026-11-16, дополнено 2026-11-17)

1. **GPUI на этапе 0.** `gpui` и `gpui_platform` подключаются на этапе 0 —
   достаточно пустого окна с заголовком и `PlayerView` без логики. Этап 4
   добавляет работу с поверхностью кадра, а не сам UI-стек.
2. **Перемотка.** На этапе 1 — простая перемотка через `Seek` (сброс
   декодеров, продолжение с новой позиции). `epoch`, очистка очередей и
   защита от гонок при быстрых повторных перемотках — этап 6.
3. **Тест этапа 1.** Берём более строгий вариант из `RULES.md`: автотест по
   числу отданных сэмплов для известного файла плюс проверка на слух.
4. **Имя файла правил.** Документ живёт в `RULES.md`, заголовок внутри
   исправлен на `# RULES`, упоминание `CLAUDE.md` в `PLAN.md` заменено на
   `RULES.md`.
5. **Кадры на этапе 4 (2026-11-16).** Кадры передаются отдельным ограниченным
   каналом (`Player::try_recv_frame`), а не событием `NewFrame`:
   неограниченный канал событий забивается кадрами и теряет отзывчивость.
   `Player::video_info()` отдаёт метаданные синхронно, без нового события.
   Рисование — через `canvas` и динамические BGRA-текстуры `gpui-fast`, без
   `img`/`RenderImage`: текстура живёт вне атласа и не раздувает его на каждом
   кадре.
6. **Пейсинг на этапе 5 (2026-11-16).** Синхронизацию решает ядро: один
   ожидающий кадр сравнивается с аудио-часами (окно 10 мс вперёд, 50 мс
   опоздания), UI забирает готовое. Для файлов без звука работает
   `VideoTimer`. Статистика приходит событием `Stats` раз в 500 мс, оверлей
   показывает fps, пропуски и отставание. Очередь кадров очищается на
   `Seek`/`Open`; полноценный `epoch` для гонок — этап 6.
7. **`epoch` и управление (2026-11-16).** Поколение кадров — внутреннее:
   `EngineMessage` и `TaggedFrame`, публичный `Command` не меняется;
   `Player::try_recv_frame` отбрасывает кадры старых поколений, включая уже
   лежащие в канале. Слайдеры считают долю по границам, которые сообщает
   `canvas`; автоскрытие панели (2 с) живёт в `PlayerWindow`, а не в
   библиотечном `VideoPlayer`.
8. **Точная перемотка (2026-11-16, после проверки владельцем).** FFmpeg
   перематывает только на ключевой кадр, поэтому `VideoDecoder::seek` сам
   декодирует и выбрасывает кадры до цели — без конвертации в BGRA — и отдаёт
   первый кадр на/после позиции. На время поиска звук ставится на паузу, чтобы
   аудио-часы не убежали вперёд. Drag по полосе не шлёт поток `Seek`: он
   обновляет предпросмотр, а команда уходит один раз при отпускании мыши.
9. **Надёжность (2026-11-17).** Пустой файл проверяется по метаданным до
   FFmpeg и Symphonia и сообщается вариантом `EmptyFile`; иначе пользователь
   получал бы «формат не поддерживается» без причины. `Event::Buffering`
   удалён из контракта: локальные файлы не буферизуются. `Loading` не введён —
   открытие синхронно. Библиотеки пишут через фасад `tracing`, подписчик —
   только в бинарниках; по умолчанию `warn`, `RUST_LOG=info` включает ключевые
   события.
10. **Кодеки и AV1 (2026-11-17).** «Все кодеки» означают все, которые умеет
    декодировать конкретная сборка FFmpeg: H.264, HEVC, VP8/VP9, MPEG, ProRes
    и большинство остальных идут встроенными декодерами. Встроенный `av1` в
    FFmpeg умеет только аппаратное декодирование, поэтому программное AV1
    включено через `libdav1d` (`ffmpeg[dav1d]` в vcpkg). Если кодек в сборке
    отсутствует, `ENOSYS` превращается в текст с подсказкой, а не в
    «Function not implemented».
11. **Звук и хвост видео (2026-11-17).** Symphonia остаётся основным
    аудио-бэкендом, но Opus (WebM/MKV) в 0.5.5 не декодируется. Поэтому
    `AudioDecoder` — перечисление из двух бэкендов: Symphonia, затем FFmpeg;
    наружу оба отдают одинаковый `AudioChunk`, так что часы и rodio не знают о
    подмене. Symphonia открывает дорожку и сразу декодирует первый блок:
    заголовок MP4 не всегда сообщает число каналов (`stsd`), и настоящие
    каналы и частота берутся из спецификации декодированного блока — иначе
    стерео ушло бы в вывод как моно, с неверной скоростью и часами. Когда звук
    закончился и его очередь опустела, видео ведёт запасной таймер,
    перебазированный на последний показанный кадр: иначе последние кадры с
    большим PTS вечно ждали бы стоящие аудио-часы и файл не доходил бы до
    `Ended`. Для файлов без звука `PositionChanged` тоже отправляется — от
    таймера видео. Выходной кадр swresample выделяется под каждый входной
    кадр: переиспользование буфера, выделенного под первый Opus-пакет (он
    короче из-за pre-skip), молча обрезало каждый следующий пакет — звук
    заканчивался на 115 с при длительности 170 с и рассинхронивался после
    перемотки.
12. **Пул BGRA-буферов (2026-11-17).** Кадр 1080p — 8.3 МБ, на 30 fps это
    ≈ 250 МБ/с аллокаций. Замер показал, что debug и release дают одинаковые
    289 fps, то есть узкое место — не код на Rust, а C-вызовы FFmpeg и
    выделение памяти; единственный заметный запас здесь. Пул живёт в потоке
    ядра, а буферы возвращают потребители. Публичный API расширен аддитивно:
    `Player::recycle_frame(VideoFrame)`; приватного поля у `VideoFrame` нет,
    поэтому внешний код по-прежнему собирает кадр литералом.
    `VideoDecoder::next_frame_with_buffer` — `pub(crate)`,
    `FrameConverter::convert_into` — приватный. Пул ограничен
    `QUEUED_FRAMES + 2` буферами и очищается на `Open` (у нового файла может
    быть другое разрешение), поэтому память не растёт: RSS ровные 63 МБ
    против колебаний 47–55 МБ до пула. Если потребитель забудет вернуть
    буфер, ядро выделит новый — корректность от этого не зависит, пул нужен
    только ради скорости.
13. **Полировка, шаг 1 (2026-11-17).** Отдельные зависимости для UI не
    добавляем: у GPUI уже есть родной диалог выбора файла
    (`App::prompt_for_paths`, на Windows — системный), поэтому `rfd` не нужен,
    и приём перетаскивания (`ExternalPaths` + `on_drop`). Диалог вызывается
    из кнопки «Открыть», клавиши `O`/`Ctrl+O` и через drop; открывается один
    файл — плейлист решено не делать (см. 11.14). Иконки кнопок —
    монохромные SVG, встроенные в `player-gpui/src/icons.rs` (а не файлы в
    `assets/`): GPUI растеризует SVG в альфа-маску и красит её цветом текста
    элемента, поэтому один рисунок годится для светлой и тёмной кнопки, и
    нет ни подстановки ассетов, ни риска «файл не найден». Текст с кнопок
    убран, но названия сохранены в `aria_label` — иначе кнопки были бы
    безымянными для скринридера. Чтобы заменить рисунки, достаточно поправить
    `Icon::svg` (требования: `viewBox="0 0 24 24"`, `width`/`height` = 24,
    монохром).
14. **Границы этапа 9 (2026-11-17).** Владелец решил не делать плейлист и
    запоминание позиции просмотра — в этапе 9 их нет. Иконки кнопок остаются
    нарисованными агентом. Меню — выпадающее **внутри окна** (системного меню
    в этой версии GPUI на Windows нет: `App::set_menus` только складывает
    пункты в состояние), состав — «Открыть…», «Показать/Скрыть оверлей
    статистики», «О программе», «Автоскрытие панели». Отдельной панели
    настроек нет: два переключателя живут прямо в меню, состояние хранится в
    памяти процесса (файла конфигурации не делаем). «Иконка» — иконка
    **exe-файла**: в `WindowOptions` поля иконки нет, файл
    `assets/app-icon.ico` (16/24/32/48/64/128/256, собран из
    `assets/icon.png`) вшит через `build.rs` + `embed-resource` (сделано
    2026-11-18). «Упаковка» — портативная папка и два выбранных установщика
    для текущего пользователя: Inno Setup 7 и MSI (WiX v3). Подробности —
    раздел 15. Использование как библиотеки — раздел 14.
15. **Меню «⋯» (2026-11-17).** Меню — обычная `Div`-панель внутри окна, а не
    системное меню: то же решение, что в 11.14. Позиционирование далось двумя
    ошибками. Сначала список рисовался абсолютно над кнопкой, то есть за
    границами панели управления, и мышь до него не доходила. Затем появилась
    прозрачная подложка на всё окно — и клики по пунктам стал забирать её
    обработчик. Причина общая и неочевидная: в GPUI `hitbox.is_hovered()`
    истинно для **всех** хитбоксов под курсором, а не только для верхнего
    (`Window::hit_test` ставит `hover_hitbox_count = ids.len()`), а
    `on_mouse_down`/`on_mouse_up` регистрируются глобально и сами
    фильтруются этим предикатом. Поэтому: 1) полноэкранная подложка под
    попапом невозможна — она всегда «наведена»; 2) обработчик «клик по кадру»
    на области кадра срабатывает и по попапу, лежащему поверх неё, и без
    защиты закрыл бы меню на mouse down, до `on_click`. Итог: список —
    обычный flex-ребёнок слоя `.absolute().size_full()` внутри области кадра
    (у слоя есть точный размер, поэтому раскладка предсказуема); у списка и у
    каждого пункта на mouse down стоит `cx.stop_propagation()`.
    Закрытие — по `Escape`, по выбору пункта и по клику на кадр вне списка.
    Тогл-пункты показывают галочку и действие в подписи («Скрыть…», пока
    оверлей виден). Пока меню или «О программе» открыты, автоскрытие панели
    приостановлено — иначе меню исчезло бы вместе с кнопкой. Видимость
    оверлея хранится в `VideoPlayer`, а не в `PlayerWindow`: её рисует
    `video_view`, и для потребителя библиотеки (`§14`) она полезна так же, как
    для демо-бинарника; настройка не сбрасывается при смене файла. Версии
    FFmpeg живут в `player-core` (`FfmpegVersions::detect`) — единственном
    крейте с зависимостью от `ffmpeg-next`; UI не начинает знать про FFmpeg.
    Номера берутся из рантайма: в `LIBAV*_VERSION_INT` старший байт — major,
    средний — minor, младший — patch.
16. **Информация о файле и снятое предупреждение (2026-11-17).** По просьбе
    владельца: 1) пункт меню «Информация о файле» виден только когда файл
    открыт и показывает только реально известное — имя, полный путь, размер
    с диска, описание контейнера, длительность, видео (кодек, разрешение,
    fps), звук (кодек, каналы, частота); 2) разрешение убрано из нижней
    панели — там остались кнопки, время и громкость; 3) плашка и проверка
    прав администратора удалены вместе с `whoami`: ограничение UIPI осталось
    только в документации и `debug`-логах перетаскивания.
    Метаданные собираются в ядре: `Player::media_info() -> MediaInfo`. Имена
    контейнера и кодеков читаются отдельным проходом по заголовку FFmpeg
    (`probe_tracks`): Symphonia не даёт короткое имя кодека в том же виде, а у
    файла без видео нет и `VideoDecoder`. Разрешение и fps берутся из
    открытого видеодекодера, каналы и частота — из аудиодекодера (заголовок
    MP4 врёт про каналы). Ошибка чтения заголовка не фатальна: файл уже
    открыт, просто часть строк не появится. Панели «Информация о файле» и
    «О программе» — один `message_panel` с разными строками и шириной.
    Для потребителя библиотеки типы реэкспортированы из `player-gpui`
    (`MediaInfo`, `VideoTrackInfo`, `AudioTrackInfo`).
17. **Превью и панель без кнопки «Открыть» (2026-11-17).** Владелец попросил
    убрать левую кнопку-папку из панели и надпись «готов к воспроизведению»:
    1. открытие файла — только `O`/`Ctrl+O`, пункт меню «Открыть…» и
       перетаскивание (иконка `Icon::Open` удалена — вариантов иконок стало 7);
    2. вместо надписи показывается превью. Ядро декодирует видео только по
       `Play`, поэтому первый кадр берётся один раз при открытии:
       `player_core::preview_frame(&path)` открывает файл ещё раз, декодирует
       ровно один кадр и закрывает декодер (~10–30 мс в потоке UI, файлы
       локальные). Отдельной команды ядра и второго долгоживущего декодера
       поэтому не появилось, а цикл воспроизведения не трогаем — первая
       показанная превью-картинка просто заменяется кадром из ядра при старте.
       Ошибка превью не фатальна: остаётся чёрное поле (в `debug`-лог пишется
       причина). Буфер превью потом возвращается в пул ядра как обычный кадр —
       размер совпадает, так что пул его переиспользует;
    3. файл без видеодорожки показывает иконку ноты и надпись «Аудио файл» —
       кадра у него не будет никогда. Тексты остались только там, где без них
       непонятно: `Idle` («видео не открыто»), `Playing` до первого кадра,
       `Ended` и `Failed`.
18. **Панель поверх кадра (2026-11-17).** Владелец попросил, чтобы панель
    управления не уменьшала видео при появлении, а лежала поверх него и была
    слегка прозрачной. Поэтому панель — не элемент колонки `root`, а
    наложение внутри области кадра (`controls_panel()`:
    `.absolute().left_0().bottom_0().w_full()`), фон `rgba(0x11_11_11_cc)` —
    около 80 % непрозрачности, чтобы кадр просвечивал. Что из этого следует:
    1. картинка всегда занимает всё окно, и в нижние ≈52 px кадра попадает
       панель (при letterbox там обычно чёрные поля); 2) при автоскрытии видео
       открывается целиком; 3) меню «⋯» отсчитывает отступ от
       `CONTROLS_HEIGHT = 60` (высота панели + зазор) — при смене `py_3` или
       размера кнопок константу надо править; 4) панель лежит внутри области
       кадра и **гасит всплытие** `on_mouse_down`, поэтому клик по её кнопкам
       не доходит до области «клик по кадру» — иначе он переключал бы
       воспроизведение и закрывал открытые панели/меню (исправлено
       2026-11-18).
19. **Клик по панели не переключает паузу (2026-11-18).** Владелец
    обнаружил, что нажатие на любую кнопку нижней панели заодно играло или
    ставило видео на паузу. Причина та же, что в пункте 15: в GPUI
    `hitbox.is_hovered()` истинно для всех хитбоксов под курсором, а панель —
    наложение поверх полноэкранного `div` с `on_click`. Меню «⋯» гасило
    всплытие, а сама панель — нет. В `controls_panel()` добавлен
    `on_mouse_down(…, cx.stop_propagation())`. Порядок регистрации
    обработчиков такой, что родитель регистрируется раньше детей, а
    bubble-фаза идёт обратно — кнопки успевают записать свой клик до того,
    как панель остановит распространение.
20. **Play без открытого файла (2026-11-18).** В `Idle` кнопка Play открывает
    системный диалог выбора файла, а не бездействует: `play_action(state)` в
    `controls.rs` даёт `OpenFile` для `Idle` и `TogglePlayback` для остальных
    состояний (решение принимается по `video.state()` в момент клика, а не по
    состоянию прошлой отрисовки). Иконка остаётся `Play`, `aria_label` —
    «Открыть видео». После выбора файл открывается как обычно (превью, `Ready`)
    и его запускает та же кнопка. Горячие клавиши и клик по пустому кадру
    остаются прежними: выбор файла — `O`, меню или кнопка Play.

## 12. Решения по инфраструктуре (2026-11-16, дополнено 2026-11-17)

1. **CI** — GitHub Actions, `.github/workflows/ci.yml`: один job на
   `ubuntu-latest`. Перед сборкой ставится набор системных библиотек, который
   требует GPUI на Linux (wayland, xkbcommon, fontconfig, freetype, vulkan,
   alsa, ssl, zstd), а также dev-пакеты FFmpeg (`libav*-dev`) и `clang` +
   `libclang-dev` для bindgen из `ffmpeg-sys-next`; `gtk`/`webkit` не
   ставим — они нужны только для нативной композиции, которой в проекте нет.
   Шаги: `cargo fmt --all --check`,
   `cargo clippy --workspace --all-targets -- -D warnings`,
   `cargo test --workspace`. Windows-раннер добавим, если он понадобится для
   платформенных проверок GPUI.
2. **Тестовые ассеты** генерируются локально, в git не попадают
   (`/assets/test/*`, исключение — `README.md`). Сгенерированы:
   `sync_test.mp4` (30 с, H.264 + AAC), `sync_test.webm` (30 с, VP9 + Opus),
   `audio_only.m4a`, `video_only.mp4`, `empty.mp4`, `truncated.mp4`,
   `av1_test.webm` (2 с, AV1 для проверки `libdav1d`),
   `bench_10min_1080p.mp4` (10 минут, 1080p30, для замера производительности).
   Команды — в `assets/test/README.md`.
3. **Заметок в `docs/` сверх `SPEC.md` и `CURRENT_TASK.md` пока нет.**
   `PLAN.md` и `RULES.md` остаются в корне как документы владельца;
   `docs/SPEC.md` — их сводка для работы.
4. **FFmpeg на Windows (решено 2026-11-16, дополнено 2026-11-17).** vcpkg в
   `Program Files` неизменяем, поэтому в проекте разворачивается свой рут —
   `.tools/vcpkg` (каталог в `.gitignore`). Установлен `ffmpeg 9.0.2` (триплет
   `x64-windows`, сборка ~10 мин): avcodec, avdevice, avfilter, avformat,
   swresample, swscale и внешний декодер `dav1d` для AV1; остальные кодеки
   берутся из встроенных декодеров FFmpeg. Путь к `.pc`-файлам прописан в
   `.cargo/config.toml` через `PKG_CONFIG_PATH`, поэтому `cargo build` находит
   библиотеки сам.

   Сборка воспроизводится так (2026-11-17 добавлена фича `dav1d`):

   ```bash
   git clone --depth 1 https://github.com/microsoft/vcpkg.git .tools/vcpkg
   .tools/vcpkg/bootstrap-vcpkg.bat -disableMetrics
   .tools/vcpkg/vcpkg install "ffmpeg[avcodec,avdevice,avfilter,avformat,swresample,swscale,dav1d]" --triplet x64-windows --recurse
   ```

   `--recurse` нужен, чтобы пересобрать уже установленный `ffmpeg` при
   добавлении фичи.

   Сборка динамическая: FFmpeg и `dav1d` — это DLL, поэтому перед первым
   запуском (и после `cargo clean`) копируем их рядом с бинарниками:

   ```bash
   cp .tools/vcpkg/installed/x64-windows/bin/*.dll target/debug/
   cp .tools/vcpkg/installed/x64-windows/bin/*.dll target/debug/deps/
   ```

   **Сборка из Git Bash (важно для будущих сессий).** В `PATH` Git Bash
   первым оказывается `/usr/bin/link.exe` (GNU-утилита), и компоновка падает с
   `extra operand …rcgu.o`. Обход — встроенный линкер Rust:

   ```bash
   RUSTFLAGS="-Clinker=rust-lld" cargo build
   ```

   Из PowerShell проблемы нет: там первым находится `link.exe` из MSVC.

5. **4K и аппаратное декодирование** — не входят в приёмку этапа 8. Критерий
   этапа 8 остаётся «10 минут 1080p без роста памяти и без пропусков»; 4K и
   аппаратный путь — отдельное расширение после него.
6. **Согласования 2026-11-16 (после этапа 1).** `video_view` остаётся
   заглушкой до этапа 4; громкость — шкалой из 10 шагов до этапа 6;
   реализацию ключевых частей (часы; в будущем — очередь кадров и `epoch`)
   пишет агент целиком, владелец смотрит готовый код и задаёт вопросы. Это
   согласованное отступление от пункта 4 `RULES.md` («ключевые части пишу
   сам»).
7. **Тестовое видео (2026-11-16).** Автотест берёт
   `assets/test/video_only.mp4`, если он есть; иначе генерирует клип
   системным `ffmpeg` во временном каталоге; если `ffmpeg` нет — тест
   пропускается с явным сообщением. Так CI получает покрытие, а в git

### 13.1 Замеры «до/после»

H.264; звук — тишина (для декодера та же нагрузка, но 10-минутный прогон не
шумит). Сборка debug, как у владельца в `cargo run`.

| --------------------------- | ------------------------ | ------------------------ |
| Кадры                       | 18000/18000, `dropped 0` | 18000/18000, `dropped 0` |
| fps / конец файла           | 30.0, `ended` на 600 с   | 30.0, `ended` на 600 с   |

Последняя строка — путь без пула: там каждый кадр по-прежнему выделяется

| Что делает                                              | Время  | На кадр |
| ------------------------------------------------------- | ------ | ------- |
| только декод (`-f null -`)                              | 5.2 с  | 0.29 мс |
| декод + swscale в BGRA                                  | 14.8 с | 0.82 мс |
| декод + BGRA + запись кадра целиком (`-f rawvideo NUL`) | 38.0 с | 2.11 мс |

Вывод: после пула видео-путь стоит ≈ столько же, сколько «пол» FFmpeg
(2.11 мс/кадр с учётом копии готового кадра). Остаток полного CPU — звук,
цикл движка и события (≈1 мс/кадр по разности).

### 13.2 Почему пул, а не микрооптимизации

Декодер даёт одинаковые 288.6 fps в debug и 289.3 fps в release. Это значит,
что в видео-пути узкое место — не код на Rust, а C-вызовы FFmpeg и память
(зависимости в dev-профиле и так собираются с `opt-level = 3`, свой код — с
`opt-level = 1`). Единственный измеримый запас был в аллокации BGRA-буфера
на каждый кадр: 8.3 МБ × 30 раз/с ≈ 250 МБ/с. Его и убрали пулом:
`Player::recycle_frame`, `VideoDecoder::next_frame_with_buffer`,
`FrameConverter::convert_into` (см. §11.12).

### 13.3 Что осталось из аллокаций

| Место                                                                      | Частота и объём                                   | Вердикт                                                       |
| -------------------------------------------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------- |
| `audio::chunk_from` (Symphonia): `SampleBuffer::new` + `to_vec()`          | 2 аллокации + 2 копии по ≈7.7 КБ, ≈47 раз/с       | Шум; убирается своим буфером в декодере                       |
| `rodio::buffer::SamplesBuffer::new`                                        | Внутри делает `Arc<[f32]>` — ещё одна копия блока | Убирается только своим `Source` поверх `Vec<f32>` (~30 строк) |
| `FfmpegFrame::empty()` и `Packet::empty()` в декодере                      | ≈30–60 раз/с, ≈100 байт                           | Внутри аллокатора FFmpeg, трогать бессмысленно                |
| UI: `format_clock` ×2, `format_resolution`, `format!` для «%» и статистики | ≈5 `String` на перерисовку, ≈50 перерисовок/с     | Можно кэшировать в сущности; выигрыш — микросекунды           |
| `VideoPlayer::drain_events`: `collect::<Vec<_>>()`                         | один маленький `Vec` на опрос с событиями         | Заменить на `while let` ради чистоты                          |
| Ошибки, логи                                                               | раз на событие                                    | В горячем пути отсутствуют                                    |

### 13.4 Что делать не нужно (и почему)

- **`Vec::with_capacity` как «оптимизация».** Она не убирает аллокацию, только
  реаллокации при росте. В старом конвертере она уже была — и кадр всё равно
  выделял 8.3 МБ на каждый кадр. Сильнее вариант «взять готовый буфер и
  `clear()`». `with_capacity` уместна там, где коллекция собирается один раз
  и её размер известен (`SampleBuffer`, генераторы в тестах).
- **Строки → `Vec<u8>`/`&[u8]`.** `String` в Rust — это уже `Vec<u8>` с
  инвариантом UTF-8; замена ничего не экономит, но теряет гарантию кодировки
  и читаемость. Текст у нас только в UI (`SharedString` на `SmolStr` — строки
  до ≈22 байт живут инлайн, без кучи), в ошибках и в логах. Байты вместо строк
  имеют смысл для бинарных данных (пиксели — уже `Vec<u8>`) и для текста,
  который приходит снаружи и не должен перекодироваться (субтитры — если
  появятся).
- **Микрооптимизации Rust в видео-пути** (`#[inline(always)]`,
  `-C target-cpu=native`, ручные циклы): по цифрам выше они не видны.

### 13.5 Где настоящий запас

1. **Копия кадра в GPU-текстуру** — 8.3 МБ × 30 раз/с ≈ 250 МБ/с плюс столько
   же пишет swscale. В CLI-замерах этого не видно, в окне — видно. Лечится
   переходом на YUV-текстуру с конвертацией на GPU (менять подход, а не
   микрооптимизировать).
2. **Аппаратное декодирование** (D3D11VA и аналоги) — вне приёмки этапа 8
   (раздел 12.5).
3. **4K** — тоже вне приёмки; при нём стоимость кадра и текстуры растёт в
   4 раза, и пункт 1 станет главным.

### 13.6 Приоритеты, если браться дальше

1. YUV-текстура без конвертации на CPU — самый крупный оставшийся расход.
2. Свой `Source` в звуке вместо `SamplesBuffer` — убирает одну копию блока
   (≈0.4 МБ/с, эффект в пределах шума; делать ради чистоты, не ради цифр).
3. Кэш форматированных строк в UI — чистота UI-пути, не скорость.

Пока всё это не понадобилось: приёмка этапа 8 выполнена, приложение тратит
≈10 % одного ядра на 1080p30.

## 14. Использование как библиотека (2026-11-17)

Цель: чужой проект на GPUI подключает `player-gpui` и получает готовый
видеоплеер, не трогая FFmpeg/Symphonia/rodio напрямую.

### 14.1 Что отдаёт библиотека

| Экспорт                                         | Назначение                                                                                                   |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `VideoPlayer`                                   | сущность: состояние, команды, кадры; `VideoPlayer::create(path, cx)` или `cx.new(VideoPlayer::new)` + `open` |
| `video_view(&player, cx)`                       | кадр с letterbox, оверлей статистики и кнопка «Повторить»                                                    |
| `controls_view(&player, cx)`                    | готовая панель с кнопками-иконками и слайдерами (необязательна)                                              |
| `run_app(Option<PathBuf>)`                      | готовая оболочка окна — для бинарника и примеров                                                             |
| `MediaInfo`, `VideoTrackInfo`, `AudioTrackInfo` | метаданные открытого файла: контейнер, кодеки, звук                                                          |
| `PlaybackState`                                 | `Idle`, `Ready`, `Playing`, `Paused`, `Ended`, `Failed`; `is_playing()`                                      |
| `LaunchError`, `WINDOW_TITLE`                   | вспомогательные типы                                                                                         |
| `gpui`, `gpui_platform` (реэкспорт)             | гарантирует одну версию GPUI и один платформенный слой у библиотеки и потребителя                            |

Команды ядра (`player_core::Command`/`Event`) потребителю не нужны — он зовёт
методы `VideoPlayer`.

### 14.2 Как подключить

```toml
[dependencies]
gpui = { package = "gpui-fast", version = "0.1.16" }
player-gpui = { path = "../vgpu-player/crates/player-gpui" }
# после тега: player-gpui = { git = "https://github.com/m1Ck1-pypy/vgpu-player.git", tag = "v0.1.0", package = "player-gpui" }
```

Версия `gpui` у потребителя и внутри библиотеки должна совпадать (два GPUI в
одном процессе не соберутся) — поэтому лучше импортировать GPUI через
`player_gpui::gpui`.

### 14.3 Минимальное встраивание

```rust
use gpui::prelude::*;
use player_gpui::{VideoPlayer, controls_view, video_view};

struct Screen {
    player: gpui::Entity<VideoPlayer>,
}

impl gpui::Render for Screen {
    fn render(
        &mut self,
        _: &mut gpui::Window,
        cx: &mut gpui::Context<Self>,
    ) -> impl gpui::IntoElement {
        gpui::div()
            .flex()
            .flex_col()
            .size_full()
            .child(video_view(&self.player, cx).flex_1())
            .child(controls_view(&self.player, cx))
    }
}

// создание: VideoPlayer::create(path, cx);
// управление: player.update(cx, |v, cx| v.toggle_playback(cx));
```

Если нужен свой UI, `controls_view` не вызывается, а всё делается методами
`VideoPlayer`: `play`/`pause`/`toggle_playback`, `seek`, `set_volume`,
`toggle_mute`, `open_dialog`, `open_dropped`, `restart`, `retry`, плюс
чтение состояния (`state`, `position`, `duration`, `video_info`, `stats`).

### 14.4 Что нужно на машине потребителя

- Windows: рядом с его exe должны лежать DLL FFmpeg (`avcodec-63`,
  `avdevice-63`, `avfilter-12`, `avformat-63`, `avutil-61`, `swresample-7`,
  `swscale-10`, `dav1d`) — тот же набор, что и для `player-app` (раздел 15).
- Звуковое устройство по умолчанию: без него `Player::open` вернёт ошибку и в
  окне появится экран ошибки.
- Перетаскивание файлов не работает в процессе с правами администратора
  (UIPI). Собственной проверки в библиотеке нет — она была в демо-окне и
  удалена 2026-11-17 (§11.16); ограничение важно знать, если потребитель сам
  включает приём `ExternalPaths`.

### 14.5 Примеры (2026-11-17)

| Файл                                          | Что показывает                                                           | Запуск                                                      |
| --------------------------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------- |
| `crates/player-gpui/examples/embed_in_app.rs` | встраивание `video_view` в своё окно и свои кнопки — без `controls_view` | `cargo run -p player-gpui --example embed_in_app -- <файл>` |
| `crates/player-gpui/examples/minimal.rs`      | минимум кода: `run_app(Some(path))`                                      | `cargo run -p player-gpui --example minimal -- <файл>`      |

Требования к примерам:

- только публичный API библиотеки, без `player-core` напрямую;
- `embed_in_app`: своё окно (`WindowOptions`), `video_view` + собственные
  кнопки (play/pause, перемотка), чтение `state()`/`position()`/`duration()`,
  открытие файла аргументом и через `open_dialog` — чтобы было видно, что
  библиотеку можно взять без готовой панели;
- `minimal`: максимум 10 строк в `main`;
- без `unwrap()`/`expect()` в рабочем коде (в примерах допустимо, но лучше
  сообщать об ошибке в stderr и завершаться кодом 1, как `player-app`).

Проверка: `cargo build -p player-gpui --examples` и оба запуска с файлом
`assets/test/sync_test.mp4` (`just example-minimal`, `just example-embed` или
`cargo run -p player-gpui --example ...`); примеры входят в
`cargo clippy --all-targets`.

**Статус 2026-11-17:** оба примера написаны и проверены — собираются,
проходят `clippy -D warnings`, запускаются с файлом. Для запуска примеров
DLL FFmpeg нужно положить ещё и в `target/debug/examples/` (рядом с их exe);
команда — в `crates/player-gpui/README.md`.

## 15. Упаковка и установщики (2026-11-18)

### 15.1 Портативная папка (2026-11-17)

1. `cargo build --release -p player-app`;
2. скопировать DLL FFmpeg рядом с release-бинарником (тот же набор, что для
   debug): `cp .tools/vcpkg/installed/x64-windows/bin/*.dll target/release/`;
3. собрать папку:

   ```text
   dist/vgpu-player/
     player-app.exe
     avcodec-63.dll  avdevice-63.dll  avfilter-12.dll  avformat-63.dll
     avutil-61.dll  swresample-7.dll  swscale-10.dll  dav1d.dll
   ```

   `avdevice` и `avfilter` нужны: exe импортирует `avdevice-63.dll`, а та —
   `avfilter-12.dll` (проверено `objdump -p`). `pkgconf-8.dll` из каталога
   vcpkg — инструмент сборки, в поставку не входит;

4. имена версий DLL берутся какие есть в `.tools/vcpkg/installed/x64-windows/bin`
   — список в этом разделе уточнён по факту, а не скопирован вслепую;
5. проверка: запустить `dist/vgpu-player/player-app.exe <файл>` **двойным
   кликом из Проводника**, а не из терминала разработчика: только так видно,
   что DLL находятся; drag-and-drop и воспроизведение работают. Запуск из
   папки с файлом агентом проверен; двойной клик — за владельцем. В release
   exe имеет подсистему Windows GUI: консольное окно не появляется (в debug
   остаётся CUI ради логов);
6. инструкция (что положить рядом, что такое UIPI-ограничение) — в
   `crates/player-gpui/README.md` (раздел «Windows: что положить рядом»);
   новых файлов верхнего уровня без согласия не заводим.

`dist/` — артефакт сборки, не в git (добавлен в `.gitignore`).

### 15.2 Установщики (2026-11-18)

Выбраны **два** установщика: **Inno Setup** для обычных пользователей и **MSI**
для управляемой установки. Оба ставят приложение для текущего пользователя
(без UAC), чтобы оно потом работало обычным процессом и drag-and-drop не
ломался (UIPI). Артефакты лежат в `dist/` (в git не попадают). Пересборка
обоих — `just installers` (см. `justfile`).

Почему так:

- Inno Setup нужен для обычного сценария «скачал и запустил»: мастер, русский
  и английский языки, ярлыки, деинсталлятор — всё без UAC;
- MSI нужен для управляемой установки (Intune/GPO, инвентаризация,
  стандартное удаление); это второй, принципиально другой формат;
- NSIS дублирует Inno Setup по роли, поэтому в проекте его нет. При
  необходимости NSIS можно использовать **вместо** Inno Setup: он полностью
  свободен (в том числе для коммерческого распространения), а Inno Setup 7
  печатает `Non-commercial use only`.

#### Inno Setup 7 — `vgpu-player-0.1.0-setup.exe`

- Скрипт: `installer/vgpu-player.iss`; установка в
  `%LOCALAPPDATA%\Programs\vgpu-player`, `PrivilegesRequired=lowest`.
- Ярлык в «Пуск», опциональный ярлык на рабочем столе, деинсталлятор;
  `assets/app-icon.ico` — для установщика и ярлыков.
- Сборка: `"C:\Program Files\Inno Setup 7\ISCC.exe" installer/vgpu-player.iss`
  (в `PATH` компилятора нет). На машине **Inno Setup 7.1.1**; компилятор
  печатает `Non-commercial use only` — для коммерческого распространения
  нужна лицензия Inno Setup или NSIS (примечание выше).
- Проверено: тихая установка, запуск установленного exe с файлом, удаление.

#### MSI (WiX Toolset v3.14.1) — `vgpu-player-0.1.0.msi`

- Исходники: `installer/vgpu-player.wxs` + `installer/AppFiles.wxs`;
  `InstallScope="perUser"`, установка в `%LOCALAPPDATA%\vgpu-player`
  (без промежуточного `Programs`: иначе ICE64 требует удалять общий каталог).
- Компоненты файлов используют HKCU-keypath — требование ICE38 для per-user.
  `light` выдаёт ICE91 как предупреждение о per-user каталоге, это ожидаемо.
- Сборка из корня репозитория:

  ```text
  mkdir target\wix
  .tools\wix\candle.exe -arch x64 -dSourceDir=dist\vgpu-player -o target\wix\ installer\vgpu-player.wxs installer\AppFiles.wxs
  .tools\wix\light.exe -ext .tools\wix\WixUIExtension.dll -pdbout target\wix\vgpu-player.wixpdb -o dist\vgpu-player-0.1.0.msi target\wix\vgpu-player.wixobj target\wix\AppFiles.wixobj
  ```

- WiX 3.14.1 скачан в `.tools/wix` (в git не входит). `AppFiles.wxs`
  поддерживается вручную: список DLL надо обновлять при изменении набора.
- Проверено: установка, запуск, удаление.

Оба выбранных установщика берут файлы из `dist/vgpu-player/` и встраивают
иконку. При смене версии правятся `MyAppVersion` (Inno) и `Version` (WiX).

**Отображаемое имя (2026-11-18).** В окне, панели «О программе», списке
установленных программ и ярлыках приложение называется **«VGPU Player»**
(`WINDOW_TITLE`, Inno `AppName`/`AppPublisher`/ярлыки, WiX `Product Name`,
`Manufacturer`, `Shortcut`, `Feature`). Имена каталогов (`%LOCALAPPDATA%\
Programs\vgpu-player`, `%LOCALAPPDATA%\vgpu-player`), файлов установщиков
(`vgpu-player-0.1.0-setup.exe`, `vgpu-player-0.1.0.msi`), exe и крейтов
остаются `vgpu-player`: это идентификаторы путей и артефактов, их смена сломала бы
обновление и деинсталляцию. Артефакты пересобраны 2026-11-18; в MSI и
`setup.exe` новое имя есть (проверено `strings -el`).

> **Альтернатива NSIS.** Если понадобится установщик без ограничения Inno
> Setup 7 `Non-commercial use only`, можно взять NSIS 3: установить его,
> написать `.nsi` по образцу `vgpu-player.iss` и собирать
> `makensis installer\vgpu-player.nsi`. В репозитории NSIS-скрипта нет.

### 15.3 CI

- `.github/workflows/ci.yml` запускается только при изменениях в
  `crates/**`, `assets/**` и `.github/**` (фильтры `paths` для `push`
  и `pull_request`). Правки только в `docs/` или в корневых файлах
  (`Cargo.toml`, `Cargo.lock`, `justfile`) прогон не запускают — это
  осознанное упрощение; при смене зависимостей тесты надо запустить вручную
  либо добавить пути в фильтр.
- После изменений 2026-11-18 правок в нём не потребовалось: новых
  зависимостей и платформенного кода нет, тесты не требуют
  медиа/дисплея/звукового устройства (клипы генерируются системным `ffmpeg`
  или тест пропускается), `embed-resource` на Linux ничего не делает, а
  apt-список закрывает нативные линковки (ASound, fontconfig, freetype,
  xkbcommon/x11, wayland, vulkan, FFmpeg, zstd).
- Первый прогон — после начальной публикации репозитория с текущим
  `ci.yml` без изменений: цель — убедиться, что Linux-сборка GPUI + FFmpeg
  проходит на `ubuntu-latest`. Результат: **прошёл без ошибок** (2026-11-18).
- Артефакты установщиков и релизы в CI — отдельная отложенная задача,
  см. §15.5.

### 15.4 Иконка приложения (2026-11-18)

- Источник: `assets/icon.png` (1023×1023, 8-bit RGBA) — прислан владельцем.
- `assets/app-icon.ico` — многоразмерный (16/24/32/48/64/128/256, 32bpp),
  собран Pillow из PNG; 256×256 хранится как PNG внутри ICO:

  ```text
  python -c "from PIL import Image; Image.open('assets/icon.png').convert('RGBA').save('assets/app-icon.ico', sizes=[(16,16),(24,24),(32,32),(48,48),(64,64),(128,128),(256,256)])"
  ```

- Вшивается в exe через `crates/player-app/build.rs` (`embed-resource` 3) и
  `crates/player-app/app.rc`: `1 ICON "../../assets/app-icon.ico"`.
  ID именно числовой: `gpui-fast-windows` загружает иконку окна через
  `LoadImageW(module, MAKEINTRESOURCE(1), ...)`, а имя `IDI_ICON1` он не
  находит — заголовок оставался с иконкой Windows по умолчанию.
- `WindowOptions` иконку не задаёт — панель задач и заголовок берут её из exe.
- Та же иконка используется в двух выбранных установщиках и ярлыках.
- Проверено: из exe извлекается иконка 32×32, `LoadImageW` по ID 1 возвращает
  HICON, у живого окна `GetClassLongPtrW(GCLP_HICON) != 0`, а на снимке
  заголовка видна оранжевая киноплёнка (а не стандартная иконка Windows).
- При замене рисунка: положить новый PNG в `assets/icon.png`, пересобрать
  `app-icon.ico` и `player-app`; `build.rs` следит за обоими файлами.

### 15.5 GitHub Releases (отложено 2026-11-18)

Цель: по тегу `v*` собирать и прикладывать к GitHub Release готовые сборки:
Windows (portable zip + установщики) и Linux (tar.gz или AppImage).
Сейчас **не реализуем**; ниже — что уже готово, предлагаемая схема и риски,
чтобы не проектировать заново.

**Что уже готово.** `just portable` и `just installers` собирают
`dist/vgpu-player/` + Inno + MSI локально; иконка вшита в exe; `Cargo.lock`
в git, поэтому сборка воспроизводима; `ci.yml` уже проверяет Linux-компиляцию.

**Предлагаемая схема.** Отдельный `.github/workflows/release.yml`
(текущий `ci.yml` не трогаем; отдельные файлы дешевле отлаживать):

1. Триггер: `push: tags: ['v*']` плюс `workflow_dispatch` для ручного прогона.
2. **Windows (`windows-latest`):** vcpkg FFmpeg с `dav1d` (команды из
   README, кэш на `.tools/vcpkg/installed`) → `cargo build --release -p
player-app` → portable zip из `dist/vgpu-player/` → Inno Setup 7 и
   WiX 3.14.1 → артефакты `vgpu-player-<tag>-windows-x64.zip`,
   `…-setup.exe`, `….msi`.
3. **Linux (`ubuntu-22.04` или `latest`):** те же apt-пакеты, что в CI →
   release-сборка `player-app` → tar.gz с бинарником (переименовать в
   `vgpu-player`), иконкой, `.desktop` и коротким README о зависимостях.
4. **Release job:** `permissions: contents: write`, `gh release create` или
   `softprops/action-gh-release`, приложить артефакты и `SHA256SUMS`.

**Риски и решения.**

- **Inno Setup 7 в CI:** Chocolatey обычно даёт 6.x, поэтому нужен пин
  официального установщика с jrsoftware (`/VERYSILENT …`) либо отказ от
  Inno в CI в пользу MSI + zip (WiX скачивается zip-ом с GitHub Releases —
  надёжнее).
- **Время и кэш:** vcpkg-сборка FFmpeg без кэша 15–25 мин; `actions/cache`
  по `.tools/vcpkg/installed` сокращает повторные прогоны.
- **Linux — не самодостаточная сборка:** нужны системные FFmpeg, Vulkan,
  Wayland/X11 и совместимая glibc. tar.gz + инструкция — минимум работы;
  AppImage/Flatpak ближе к «двойному клику», но заметно сложнее и хрупче.
- **Linux не проверен в окне:** CI только компилирует; перед первым релизом
  его нужно хотя бы раз запустить (локально/WSL), иначе можно опубликовать
  нерабочий бинарник.
- **Неподписанные артефакты:** SmartScreen будет ругаться на exe/MSI;
  подпись сертификатом — вне рамок 0.1.0.
- **Версия:** `MyAppVersion` (Inno) и `Version` (WiX) зашиты как `0.1.0`;
  для тегов нужно передавать версию параметром и сверять с `Cargo.toml`.
- **Только Windows/Linux:** macOS-сборка не планируется; Linux — без
  установщика, только архив (или AppImage по отдельному решению).

**Оценка работ.** Windows (zip + MSI + Inno) — 1–2 часа на workflow и
2–3 отладочных прогона; Linux tar.gz — ещё ~1 час; AppImage с FFmpeg
внутрь — плюс ~полдня; release-job с загрузкой и checksums — ~30 минут.

**Открытые вопросы к владельцу.** Формат Linux-сборки (tar.gz или
AppImage); оставлять ли Inno в CI или ограничиться MSI + zip; нужны ли
SHA256 и что считать версией при ручном `workflow_dispatch`.
