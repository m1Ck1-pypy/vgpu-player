## 3. `alhazen-gpui` / `alhazen-core`: что это и почему не берём как зависимость

Это не надстройка, а **полный собственный медиадвижок**:

- свои демуксеры (MP4/MOV, MKV/WebM, MPEG-TS, Ogg, ADTS, WAV);
- свои декодеры на чистом Rust (AV1/rav1d, VP9/vp9-mt, VP8, ProRes, Opus,
  Vorbis, FLAC, AAC, MP3, PCM);
- системные бэкенды: Media Foundation (Windows), VideoToolbox (macOS),
  NVDEC/VA-API (Linux), `ffmpeg` как внешний процесс;
- свой источник: `source/{file,http,memory,cache}.rs` — HTTP(S) с Range,
  переподключением и разделяемым кэшем;
- свой HLS-клиент: `hls/{playlist,segment,timeline,abr,crypto,demuxer,track,http}.rs`
  — VOD и live, TS/fMP4/CMAF, отдельная аудио-дорожка, AES-128, ABR.

| Критерий                | Оценка для нас                                                                                       |
| ----------------------- | ---------------------------------------------------------------------------------------------------- |
| Стоимость интеграции    | 2–3 дня, но затрагивает **весь** `player-core` и весь `player-gpui`                                  |
| GPUI                    | требует `gpui 0.2.2`, у нас `gpui-fast 0.1.16` — либо второй GPUI в дереве, либо смена UI-стека      |
| Рендер кадров           | `RenderImage` + `paint_surface` вместо нашей BGRA-текстуры и пула буферов (этап 8)                   |
| Что остаётся от проекта | почти ничего: `video_view`, `controls_view`, часы, синхронизация, пул, `player-app` — всё заменяется |
| Лицензия                | Apache-2.0 + обязательный NOTICE (§4(d)) в «О программе»                                             |
| Учебная цель            | README проекта: «цель — понять каждую строку». Подключение движка это свойство убивает               |
| Сборка                  | дополнительно нужен `nasm` (rav1d/AV1)                                                               |

**Вывод:** держим как **референс решений** (`source/http.rs`, `source/cache.rs`,
`hls/timeline.rs`, `hls/abr.rs`), а не как зависимость. Копировать код оттуда
нельзя без соблюдения Apache-2.0 (NOTICE); идеи и структура — можно.

зависшее чтение. Это снимает зависимость от того, какие сетевые протоколы
собраны в DLL (см. §8), и даёт отмену при закрытии окна.

## 5. Целевая архитектура (набросок, не финальное решение)

1. **`Source`** — публичный тип: локальный путь, `file://`, `http(s)://`.
   У него `display()` (для ошибок и панели информации), `is_seekable()`,
   `is_live()`.
2. **`MediaReader`** (внутренний трейт, аналог `symphonia::MediaSourceStream`):
   `read` + `seek` + длина. Реализации: файл, HTTP.
3. **HTTP-читатель:** блокирующий, `ureq` + rustls (async-рантайм не нужен —
   движок и так живёт в своём потоке), `Range`-запросы, переподключение с
   backoff, таймауты, отмена, ограниченный кэш байтов **с двумя независимыми
   курсорами** (звук и видео перематываются сами).
4. **FFmpeg** получает тот же источник через `input_from_stream`, а не URL
   строкой. `probe_tracks` тоже ходит через источник.
5. **Контракт:** `Loading` → `Buffering` → `Playing`/`Paused` → `Ended`,
   событие готовности с `MediaInfo`/`VideoInfo`, `Event::Buffering`, `is_seekable`.
6. **Поток ядра** остаётся один и тот же (`run_engine`, `player.rs:450`):
   блокирующие чтения уже живут вне UI-потока.

Почему так, а не «URL в `format::input`»: один код пути для файла и сети, свои
таймауты и отмена, и не зависим от сборки libavformat. Цена — свой читатель
(~300–500 строк) и тесты против локального HTTP-сервера.

## 6. Этапы

### 6.1 Этап 10 — источник как абстракция (без сети)

Смысл: убрать синхронное открытие и `PathBuf` из публичного контракта, **не
добавляя сети**. Поведение на локальных файлах не меняется. Это ~30 % всей
работы и нужно в любом варианте.

Задачи:

- [ ] `Source` + `SourceId` (отображаемое имя), `Command::Open(Source)`,
      `Player::open(Source)`; `PathBuf` остаётся деталью реализации.
- [ ] Ошибки `player-core` без обязательного `PathBuf`: имя источника строкой;
      тексты сохранить и обновить тесты контракта (`error.rs`, `mod tests`).
- [ ] Открытие в фоне: `open` возвращается сразу, состояние `Loading`,
      событие готовности несёт `MediaInfo` + `VideoInfo`; `Player::media_info()`
      и `video_info()` становятся доступны после него.
- [ ] `is_seekable()` и `Event::Buffering` возвращаются в контракт.
- [ ] `preview_frame` — асинхронно (или через событие), не в колбэке UI.
- [ ] UI: `PlaybackState::Loading` рисует спиннер/заглушку; «Информация о
      файле» показывает имя источника; drag-and-drop и `run_app` принимают
      `Source`.
- [ ] `player-cli` принимает `Source`.

Приёмка:

- локальный файл играет как раньше; все прежние тесты зелёные (или переписаны
  с обоснованием в этом файле);
- тест «медленный источник»: фейковый `MediaReader` с задержкой — `open`
  возвращается, UI не блокируется, кадр приходит после события готовности;
- ошибка открытия приходит событием и/или из `open` так же понятно, как сейчас.

Оценка: **3–4 дня**. Файлы: `player.rs`, `command.rs`, `error.rs`, `event.rs`,
`video_player.rs`, `app.rs`, `player-cli`, тесты + `docs/`.

### 6.2 Этап 11 — HTTP(S) VOD

- [ ] `HttpReader`: `Range`, `HEAD`/`GET`, `Content-Length`, `206`, `302`,
      chunked без длины, переподключение с backoff, таймауты, отмена.
- [ ] Ограниченный кэш байтов с двумя курсорами; вытеснение по объёму
      (ориентир — сотни МБ, а не «весь файл»).
- [ ] FFmpeg через `input_from_stream`; `probe_tracks` через тот же источник.
- [ ] `preview_frame` по URL (один кадр, отдельный короткий сеанс).
- [ ] `is_seekable = false`, если сервер не отдаёт `Range`: слайдер
      отключается, перемотка недоступна.
- [ ] Ошибки: 404/403/таймаут/обрыв/не тот контент — с URL в тексте.
- [ ] Опционально (обсудить): свои заголовки (`User-Agent`, `Referer`,
      cookies) — нужно не всем, но без этого часть ссылок не открывается.

Приёмка:

- `http://` и `https://` MP4 (faststart и moov в конце), MKV/WebM, MP3 —
  играют и перематываются;
- тесты на `tiny_http` (dev-зависимость) на `127.0.0.1`: Range, ответ 200 без
  Range, обрыв на середине, 404, медленная отдача; **сеть наружу не нужна**;
- сервер считает байты: одно соединение на источник или явно обоснованный
  второй поток;
- 10 минут HTTP-плея без роста памяти.

Оценка: **5–8 дней** (итого по этапам 10–11: **8–12 дней**).

### 6.3 Этап 12A — HLS через FFmpeg (дешёвый путь)

Если у сборки FFmpeg есть `hls` + `http(s)` (см. §8), `.m3u8` можно отдать
FFmpeg как есть.

- [ ] `Source` распознаёт `.m3u8`, `is_live`, отсутствие длительности.
- [ ] UI: индикатор LIVE, слайдер скрыт/заблокирован, `duration = None`.
- [ ] Ручной выбор качества: либо опция демуксера, либо переписанный master
      плейлист (одно качество вместо ABR).

Известные изъяны этого пути (принять осознанно):

- звук и видео открываются **двумя** независимыми HLS-демуксерами → двойной
  трафик и расхождение live-края; `probe_tracks` это усугубляет;
- нет настоящего ABR, переключение качества — переоткрытием;
- поведение на живом стриме зависит от FFmpeg, а не от нас.

Оценка: **+3–5 дней** сверх этапа 11.

### 6.4 Этап 12B — свой HLS-клиент (дорогой путь)

Вход только при выполнении **всех** условий:

1. нужен настоящий ABR и/или выбор качества без переоткрытия;
2. нужен live с управлением окном, а не «как получится»;
3. владелец готов к отдельному этапу на 3–6 недель.

Объём (ориентир по `alhazen-core/src/hls/`): плейлисты (master + media,
`EXT-X-MEDIA`, `EXT-X-MAP`, `EXT-X-DISCONTINUITY`), загрузчик сегментов,
ребазирование таймстемпов между сегментами, TS и fMP4/CMAF, packed audio,
`AES-128`, окно live и релоад плейлиста, ABR по скорости и буферу,
переключение варианта на границе сегмента. Порядок 1.5–3 тыс. строк + тесты.

Оценка: **3–6 недель**.

## 7. Матрица проверок для сети

| Сценарий                    | Как проверяем               | Ожидание                                    |
| --------------------------- | --------------------------- | ------------------------------------------- |
| `Range` поддерживается      | `tiny_http`, отдаём 206     | перемотка работает, `is_seekable = true`    |
| `Range` не поддерживается   | сервер отвечает 200         | играет, слайдер отключён, ошибка понятна    |
| Нет `Content-Length`        | chunked                     | открывается, длительность `None`            |
| Обрыв на середине           | сервер закрывает соединение | переподключение и продолжение, без паники   |
| 404 / 403 / не медиа        | статические ответы          | текст с URL, состояние `Failed`             |
| Медленная отдача            | задержка в сервере          | `Buffering`, UI не замирает                 |
| `https` с самоподписанным   | тестовый сертификат         | понятная ошибка TLS                         |
| Закрытие окна на скачивании | drop `Player`               | поток завершается быстро, без ожидания сети |
| Живой HLS                   | плейлист, который растёт    | позиция идёт, слайдер скрыт                 |
| HLS VOD                     | фиксированный плейлист      | перемотка по времени                        |

Правила тестов:

- тесты — только на `127.0.0.1`, внешняя сеть в CI не нужна;
- сеть не появляется в UI-потоке: проверяется фейковым медленным источником;
- «медленные» тесты с реальным временем помечаются и не входят в быстрый прогон.

## 8. Риски и проверки до начала работ

**Риск №1 — сетевые протоколы в нашей FFmpeg-сборке.** Ставим
`ffmpeg[avcodec,avdevice,avfilter,avformat,swresample,swscale,dav1d]` без
`openssl`/`gnutls`. Даже если `--enable-network` включён, HTTPS без TLS-бэкенда
не поднимется. Проверить:

```bash
ffmpeg -protocols            # нужны http, https, hls
ffmpeg -demuxers | findstr hls
ffmpeg -version              # смотреть configuration: --enable-network, --enable-openssl
```

Если протоколов нет — это аргумент за свой `HttpReader` (§5): он и так
планируется, а FFmpeg получает данные через `input_from_stream`.

| Риск                                | Влияние                       | Что делать                                        |
| ----------------------------------- | ----------------------------- | ------------------------------------------------- |
| Нет `Range` на сервере              | нет перемотки                 | `is_seekable = false`, честно в UI                |
| Два читателя (звук/видео)           | двойной трафик                | общий кэш с двумя курсорами (§5)                  |
| Память на кэш                       | OOM на 4K                     | лимит по объёму + вытеснение, тест на рост памяти |
| Live HLS                            | нет длительности, другое окно | отдельный UI-режим, LIVE-индикатор                |
| Сеть в UI-потоке                    | окно замирает                 | только этап 10 это лечит                          |
| `rodio`-буфер и сеть                | звук «рвётся» при просадке    | `Buffering` + пауза часов до наполнения           |
| Локальный сервер в тестах           | нестабильный CI               | фиксированный порт не занимать, `127.0.0.1:0`     |
| Лицензия при копировании из Alhazen | юридический риск              | только идеи, не код; иначе NOTICE                 |

## 9. Что принципиально не заработает

Не обещать ни в README, ни в UI:

- DRM: Widevine, FairPlay, PlayReady, `SAMPLE-AES`;
- YouTube и подобные сайты (подписанные URL, отдельные дорожки, свои
  алгоритмы) — только прямые ссылки на медиафайл/плейлист;
- DASH (`.mpd`) — распознаём и говорим «не поддерживается»;
- субтитры (WebVTT), low-latency HLS;
- скачивание на диск, офлайн-кэш между сеансами;
- авторизация на сайтах (формы, токены) — только статические заголовки, если
  решим их добавить.

Правовая оговорка: воспроизведение чужого контента — на ответственности
пользователя; никаких обходов защиты.

## 10. Вопросы к владельцу

1. **Объём:** делаем только HTTP-VOD (этапы 10–11), или HLS тоже? Если HLS —
   достаточно 12A (FFmpeg) или нужен live с ABR (12B)?

3. **Заголовки:** нужны ли свои `User-Agent`/`Referer`/cookies? Без них часть
   ссылок не откроется.
4. **Кэш:** какой предел памяти считаем нормальным (например, 256 МБ)?
5. **UI:** показывать URL в «Информации о файле» целиком или сокращать?
6. **Зависимость `alhazen-core`:** рассматриваем только как референс (моё
   предложение) или допускаем как движок?
7. **Порядок:** начинаем после тега `v0.1.0` и приёмки этапа 9?
